# Anomaly Detection over machine telemetry

Working name. An anomaly detector over the telemetry that [Sentinel](https://sentinel.pesanth.com)
already collects: a pinned dataset, labels that came from somewhere other than
the signal, a time-based split, a rolling three-sigma baseline to lose to, and an
isolation forest that currently loses to it.

**Status: the harness is complete and the measurement is blocked on data coverage.**
That sentence is the honest summary and the rest of this file explains it.

## The result, stated plainly

**The isolation forest is worse than chance at this task, and the reason is
interesting rather than a bug.** On the labelled windows it scores ROC AUC 0.246
where 0.5 is a coin flip. It is not confused; it is confidently backwards. The
periods when a known heavy job was running make up 59% of the labelled data, so
an unsupervised detector correctly concluded that the job running is the normal
state of this machine and flagged the quiet hours as the outliers.

That is a property of the dataset, not of the algorithm. It is also the single
most useful thing this repository currently demonstrates: an anomaly detector
fitted on a period where the anomaly is the majority class learns the opposite of
what you wanted, silently, while reporting nothing unusual.

| detector | precision | recall | F1 | ROC AUC | average precision |
|---|---|---|---|---|---|
| rolling mean + 3 sigma | 0.674 | 0.225 | 0.337 | 0.590 | 0.654 |
| isolation forest | 0.667 | 0.062 | 0.113 | 0.246 | 0.516 |

**These numbers are in-sample and must not be quoted as an evaluation.** They
come from `python tools/report.py --diagnostic`, which exists to prove the code
runs. The real evaluation refuses to run, and that refusal is described below.

## Why there is no held-out number yet

`python tools/report.py` splits by time, takes the labelled windows in the later
30%, and stops:

```
windows 225  train 157  test 68
labelled in test: 3 positive windows, fewer than the 5 needed before precision
and recall mean anything

Not evaluating. The harness runs; the labels do not support a number.
```

The check that produces this lives in `anomaly/evaluate.py`, not in a note to
self, because the most likely failure of a project like this is not a bad model.
It is a good-looking F1 computed over four labelled windows.

The cause is coverage. The available slice holds 19.6 hours of readings across
three disconnected segments inside a 60.8 hour span, and the one long labelled
event sits at the beginning. A time split therefore puts nearly every positive
in the training half. More days of telemetry fixes this and nothing else will.

## The data

`data/system-slice.ndjson`, 6,798 readings from one host at a 10 second cadence,
pinned by sha256 in `data/system-slice.manifest.json`.

It comes from Sentinel's **local collector spool** rather than from the HDFS
archive the PRD intends, because the Sentinel stack was not running when this was
built. Same collector and same schema, but the spool only holds what accumulated
while the broker was unreachable, which is where the 19.6 hours comes from.
`tools/export_slice.py --source hdfs` is written and ready for the archive.

Readings become 5 minute windows of 26 features. Windows do not overlap, because
overlapping windows share readings and a later time split then leaks the tail of
training into the head of testing.

## The labels, and why they are not from the signal

`labels/labels.csv`, 218 of 225 windows: 129 positive, 89 negative, and 7 left
deliberately unlabelled.

Every interval is justified by evidence outside the telemetry, generated by
`tools/seed_labels.py`:

- `nightly-history.tsv` from the job search pipeline, which records when a scan
  started
- a run log line reading "finished in 12 min"
- output file modification times, which bound the scraping and model-extraction
  stages of each run

None of those sources knows anything about CPU or memory. **If the labels came
from looking at the telemetry and calling the spiky parts anomalous, the model
would be scored on its agreement with a spike detector**, and the F1 would be
arithmetic performed on a tautology.

Windows where the ledger records no run are left out of the file rather than
labelled normal. "No scan was running" is not the same as "nothing was
happening", and a silent 0 on a window that was really a Docker build is a wrong
label that nothing would ever catch.

## Layout

```
anomaly/features.py     readings to windows: counter resets, coverage, reboots
anomaly/baseline.py     rolling mean + 3 sigma, the thing to beat
anomaly/model.py        isolation forest, deliberately boring
anomaly/evaluate.py     precision, recall, F1, and a refusal to score thin labels
anomaly/dataset.py      loading and the time-based split
anomaly/label_cli.py    the labelling tool, written before the model on purpose
tools/export_slice.py   pin a dataset from the spool or from HDFS
tools/seed_labels.py    labels from the external run ledger
tools/report.py         both detectors, side by side
```

```bash
pip install -r requirements-dev.txt
python tools/export_slice.py --source spool --kind system
python tools/seed_labels.py
python tools/report.py
python -m pytest
```

16 tests, none of which need Kafka, HDFS, a network or a Docker daemon.

## What this does not claim

- Not production ML, and it serves nobody.
- No availability or uptime language: the collector runs on one workstation.
- Not Sentinel's AI agent. That does not exist and no bullet may say it does.
- No metric here was computed on held-out data. When one is, it will say so.
